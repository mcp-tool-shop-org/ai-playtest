# AIプレイテスト

ターン制ゲームにおける、多様な家族構成を持つAIによるプレイテスト。モデルプレイヤーがゲームをプレイする — ターミナル、疑似ターミナル、またはエンジンに接続されたソケットを通じて — 複数のモデルからなる審査員団が、各プレイ記録を評価し、レポートを作成して、各セッションでゲームのどの程度が実際にプレイされたかをまとめる。

1人のプレイヤーによる1回のプレイは、そのプレイヤーが見たものを教えてくれる。同じ40ターンを5つの家族がプレイすることで、世界がどのように反応するかを教えてくれる。

**適切な状態になるまで非公開。** npmには公開しない。関連リポジトリからパスを通じて利用する。

## 誰が評価するのか

まず知っておくべきことは、多くの同様のツールが誤っている点である。**評価者は、自分のプレイを評価しない。** 各プレイ記録は、デフォルトでは1人の評価者によって評価される（`panelSize`、意見の相違を示すためにフラグを立てる — より高いスコアを平均化するためではない）。そして、プレイしているプレイヤー自身の評価は、*証言*として記録される — どこで混乱したか、何を試したか — スコアとしては記録されない。

この区別が重要である。LLMにおける、測定された自己選好の大部分は、ナルシシズムではなく、能力によるものである（37,448組のデータで、能力が一致するコントロールと比較して、約10.4%のみがそれを上回る — [Roytburg et al. 2026](https://arxiv.org/html/2601.22548)）。**しかし、残りの部分は主観的な領域に集中し、検証可能な領域では消失する** — そして、「世界は生き生きとして感じられたか」は、基準としては最も主観的である。一方、外部の検証者が評価することで精度が向上するのに対し、自己批判は積極的に精度を低下させる：Game-of-24では、自己批判した場合、精度が5%から3%に低下し、適切な検証者による評価では38%に向上する（[Stechly et al. 2024](https://arxiv.org/abs/2402.08115)）。

デフォルトは、**1人の評価者**であり、3人の評価者によるパネルではない。[Verga et al. 2024](https://arxiv.org/abs/2404.18796)（PoLL）は、GPT-4よりも7〜8倍低いコストで、人間の合意において優れた結果を出す、安価な異質なパネルを示した（κ 0.763 vs 0.627）。これは、1人の*大規模な*評価者に報酬を支払うことに対する反論であり、3つの家族が3つの独立した投票を生み出すという主張ではない。[Kohli 2026](https://arxiv.org/abs/2605.29800)は、Kishにおいて7つの家族にわたる9人の評価者を測定し、**n_eff = 2.18**であった。パネル（72.0%）は、最高の単一の評価者（71.8%）を上回らなかった。家族間のφは0.389、同じ家族内では0.437であった。`panelSize: 3`では、これは**約1.68の独立した投票**に相当する。Dawid–Skeneはこれを改善しない（Condorcetのギャップの≤11%）。[Kim et al. 2025](https://arxiv.org/abs/2506.07962)は、両方が間違っている場合、ペアは約60%の確率で合意することを発見した。したがって、追加の審査員は、より高いスコアではなく、意見の相違を示すフラグである。**予算は、評価者からプレイ回数に移行する。** `--runs 3`は記述的であり、有意性検定ではない。CLIはデフォルトで1回のプレイになるため、テストは1回のみ実行される。n=3では、p<0.05に到達することはできない（下限`2/2^n` = 0.25）。`docs/research-2.md` §Aおよび`docs/research-3.md`を参照。

これは、評価者が自分の評価から除外されることを覆すものではない。これは、Panickssery / Stechly / Huangに基づいている。

**意見の相違は報告され、平均化されない。** 意見が分かれる場合、通常は*基準*が十分に明確でないことを意味するものであり、ゲームが曖昧であるという意味ではない。したがって、意見の相違は、その数とともに記録され、各評価者の分散も表示される。

1つの家族のみを評価者に含めると、有効な評価者が存在しない。ツールは、プレイ記録を静かに著者に返すことはない。評価者パネルは形成されず、レポートには、評価が自己評価であり、それがなぜ弱いのかが記載される。構成の検証は、1つの家族から2人のプレイヤーを評価者に含めることを拒否する。2つ目の家族が存在することで、評価者パネルが形成される（[Panickssery et al. 2024](https://arxiv.org/abs/2404.13076)）。

## ドライバー — ゲームがどのように観察されるか

| ドライバー | チャネル | for |
|---|---|---|
| `stdio` | lines | 行指向のテキストゲーム（デフォルト） |
| `pty` | レンダリングされたターミナル**グリッド** | フルスクリーンのTUI（ratatui、ncurses） |
| `rpc` | TCP経由の構造化された状態 | Godot、Unreal、または計測できるもの |

順序は、チャネルがどれだけ*構造化*されているかによって決まり、これは好みの問題ではなく、意図的なものである。アクセシビリティツリーの観察は、[OSWorld](https://arxiv.org/abs/2404.07972)で、スクリーンショットのみの成功率をほぼ2倍にする（12.24% vs 5.26%）。[BALROG](https://arxiv.org/abs/2411.13543)では、*視覚情報を追加することで、いくつかのモデルのパフォーマンスが低下する*（GPT-4o 32.34% → 22.56%）。構造化されていないピクセルベースのプレイは、[VideoGameBench](https://arxiv.org/abs/2505.18134)ではほぼゼロ（ゲーム完了率0.48%）であり、[Voyager](https://arxiv.org/abs/2305.16291)は、依然として最も優れたオープンエンドのゲームエージェントであり、構造化されたAPIを使用し、ピクセルを一度も見たことがない。

したがって、スクリーンショットは観察におけるオプションの*添付ファイル*であり、唯一のチャネルであってはならない。**ゲームが自分自身を記述できる場合は、そうすべきである** — Godot 4のペーストしてすぐに使用できるオートロードについては、[docs/engine-bridge.md](docs/engine-bridge.md)を参照。`_observation()`と`_apply()`は、記述する唯一の関数であり、Unrealのルーティングも含まれる。

### なぜ`pty`がテキストゲームでも重要なのか

パイプの下では、Cプログラムのstdoutは完全にバッファリングされるため、「出力がNミリ秒間静止した」というメッセージは、「まだフラッシュされていない」という意味であり、「待機している」という意味ではない可能性がある。PTYは行バッファリングを復元し、準備完了のルールを明確にする。Windowsでは、パイプはコンソールAPIを通じて描画するゲームからの情報を一切キャプチャしない。

また、リドローがどのように見えるかも修正する。テストTUIで測定した結果、グリッドには**現在の画面の115文字**が表示され、行追加ビューには、プレイヤーが入力した内容が挿入され、*3つの矛盾したHP値*が表示された3つのリドローが積み重ねられて、**416文字**が表示される。モデルは、どれが現在の状態であるかを推測する必要がある。

`pty`には、オプションの`node-pty`と`@xterm/headless`が必要である。これらは、WindowsとmacOSに事前に構築されたものをインストールする。node-ptyはLinuxでコンパイルされる。これらがなければ、そのドライバーは、インストールコマンドを記述したエラーメッセージを表示して失敗する。それ以外は影響がない。

## 各評価者が実際に見た量

探索を行わないモデルプレイヤーは、ほとんど見たことのないゲームについて、自信を持って報告書を作成します。したがって、すべての実行には、ターン記録のみから計算されたカバレッジブロックが含まれます。追加のインストルメンテーションやモデル呼び出しは行いません。新規性の曲線、半減期、繰り返し/ループ/自己ループ率、アクションのエントロピー、および単純な `thin` / `moderate` / `broad` の読み取りと、その理由が示されます。

これは価値があるものです。なぜなら、失敗は測定され、理論的なものではないからです。
タスク指向のLLMエージェントは、以前のアクションを63.4%の確率で繰り返し、ループ率は16.0%です。これは、探索のためにトレーニングされたエージェントの24.9% / 7.7%と比較されます ([Ye et al. 2026](https://arxiv.org/html/2605.16143))。これを、バンドエージェントの繰り返しが実際にどの範囲にあるかとして解釈してください。これは、単にエージェントに探索するように促すだけでは、平均して+2.57の合格率しか得られないため、ペルソナ文字列によって得られるものではありません ([Englander et al. 2026](https://arxiv.org/html/2604.17609))。アクションのエントロピーが低いことは、効率性ではなく、低い成功率を示唆するため、入力が少なく整理されたトランスクリプトは、良い兆候ではなく、警告の兆候です。

## 結果の解釈方法

**ビルドをランク付けし、絶対的なスコアを信頼しないでください。** これは、このツールの最も重要な注意点であり、2つの独立した文献に基づいています。物語の質を評価するLLMの判断は、システムレベルでτ≈0.70に達しますが、人間の限界である0.73には及びません。一方、ストーリーレベルのτはわずか0.16〜0.25であり、BERTScoreよりもわずかに優れています ([Chhun et al. 2024](https://arxiv.org/abs/2405.13769))。自動プレイテストは同様の方法で検証されます。AIの合格率は、95,266人のプレイヤーを対象に、ρ=0.80で人間の合格率と一致します ([Roohi et al. 2021](https://arxiv.org/abs/2107.12061))。ただし、絶対的なエージェントのスキルはまったく転移しません。

したがって、「ビルドBは、*プレイヤーの反応*において、ビルドAよりも低いスコアを獲得しました」という主張は、このツールでサポートされます。「このゲームは生きている：はい」という主張はサポートされません。レポートは、この区別を明確に示すように作成されています。

**既知のギャップを明確に記述します。** エージェントのプレイテスターによって検出された問題と、人間のプレイテスターによって検出された問題との間の合意を、*エクスペリエンスの質*に関して測定した研究は、見つけることができませんでした。自動プレイテストは、難易度と能力のみに対して検証されます。このツールの中心的な前提、つまり、モデルの混乱がプレイヤーの混乱に似ているという考え方は、文献ではどちらの方向にも検証されていません。デッドスポットと混乱を、調査すべき手がかりとして扱い、結果として得られたものとして扱わないでください。

## 仕組み

1. **観察。** ドライバーは、`Observation`を生成します。常に`text`、オプションでターミナル`grid`、構造化された`state`、`image`アタッチメント、および現在有効な`actions`を生成します。また、それがプレイヤーのターンであるとどのように判断したかを記録します。ゲームから送信されたセンチネル、ターミナルレディシグナル、プロンプトパターン、または静止状態の推測です。これにより、知識と推論を区別できます。
2. **スクリプト化されたセットアップ。** `setup[].match`正規表現に一致するプロンプトは、プレイヤーなしで、ターンを消費せずに、構成から回答されます。これにより、すべてのファミリーが同じキャラクターから開始されます。
3. **プレイヤー**は、前回の入力と前回の`playerMemoryTurns`の交換に加えて、`persona`（目標とレジスタ—テスト対象のメカニズムではない）によってブリーフィングされた画面を表示し、1行で回答します。形式が正しくない回答は、`look`にフォールバックします。
4. **実行。** 観察に`actions`が含まれている場合、クリーンな応答は、`choose` / `key` / `line`にマッピングされます。クローズドセットのミスマッチは、ハーネスイベントです。ランナーは、これにゲームターンを費やすことはありません。セットアップと終了は、`kind:line`のままです。
5. **終了。** `turns`回の入力後、ランナーは`quitInputs`（例：`save`、`quit`）を送信します。これらは*ランナー*の入力であり、ターン数と証拠から除外されます。ただし、ターミナル画面は保持されます。クラッシュまたはセーブの概要は、証拠となります。
6. **審査員**（デフォルトでは、1人の著者以外の席）は、温度0で、トランスクリプトを`criteria[]`に対して評価します。追加の審査員（`panelSize`>1の場合）は、意見の相違をフラグします。ただし、より強力なスコアに平均化されることはありません。プレイ席自身の評価は、証言となります。
7. **決定的なチェック**は、ターン記録に対して実行されます。吸収型SCC（Tarjan、トラップとしてラベル付けされることはありません）、無視された入力の帰属、オプションのパーサー/勝利/死亡正規表現、進行なしのウィンドウ、エンティティの出現のヒント、および（`state`がオブジェクトの場合）HP/インベントリの不変性です。
8. **レポート**は、集計します。ファミリーごとの基準、審査員の意見の分割、カバレッジをサンプリングの資格として、検証ブロック、およびすべてのデッドスポットと混乱を名前で示します。まず審査員の意見を示し、次に著者の証言を示します。グリフ（`!`、`H(a)`、`repeat`、`loop`）は、ページに凡例として示されます。

`<runsDir>/<label>/<seat>/`の下の各席の成果物：`transcript.txt`、`critique.json`、`meta.json`（ピン`schemaVersion` + `toolVersion`）、`stderr.txt`（ゲームが何かを書き込んだ場合）。`REPORT.md`と`REPORT.json`（`kind: "single-run-report"`）は、ラベルのルートにあります。

## 使用方法

```bash
export OPENROUTER_API_KEY=...
npm run build
node dist/cli.js run path/to/game.playtest.json --label phase9
node dist/cli.js run path/to/game.playtest.json --label smoke --seats mistral --turns 8
node dist/cli.js run path/to/game.playtest.json --label compare --runs 3   # descriptive; cannot reach p<0.05
node dist/cli.js run path/to/game.playtest.json --label rpc --serial       # one game, several seats; needed for RPC until you multiplex
node dist/cli.js report path/to/game.playtest.json --label phase9   # rebuild REPORT.md + REPORT.json from disk
```

`--serial`は、席を1つずつ実行します。RPCドライバーでは、1つのTCPクライアントを再利用し、席の間に`reset()`を呼び出します。`--serial`がない場合、各RPC席は独自のプロセスになります。これらが1つのリスニングゲームを共有する場合、競合が発生します。

終了コード：0 OK · 1 使用法 · 2 構成 · 3 プロバイダー（キーがありません、モデルにはエンドポイントがありません） · 4 実行エラー（すべての席がエラーで終了するか、どの席も結果を生成しません）。エラーは、`error:`と`hint:`を出力します。

## 構成リファレンス

| キー | 意味 |
|---|---|
| `name` | プレイテスト名（レポートのタイトル） |
| `driver` | `{"kind":"stdio"}`（デフォルト）、`{"kind":"pty","cols":100,"rows":30,"readySentinel":"..."}`、または`{"kind":"rpc","port":7777,"host":"127.0.0.1"}` |
| `game.command`, `game.args`, `game.cwd` | ゲームを起動する方法。`cwd`は、構成ファイルに対して解決されます。不要な場合もあります。`rpc`ドライバーは、実行中のゲームにアタッチします。 |
| `game.env` | ゲーム用の追加の環境変数。値`$NAME`は、ランナーの環境を読み取ります。 |
| `game.inheritEnv` | ランナーの環境全体をゲームに渡します。**デフォルトではオフ**です。以下を参照してください。 |
| `game.promptPatterns` | 「行を待機している」という意味の正規表現。ストリッピングされた末尾（`stdio`）またはレンダリングされたカーソル行（`pty`）に対してテストされます。 |
| `game.promptQuietMs` / `idleQuietMs` / `screenTimeoutMs` | 待機ルール（デフォルトは800 / 6000 / 180000ミリ秒）。 |
| `game.quitInputs` | 最後のターン後に送信される行数（デフォルトは`["quit"]`）。 |
| `seats[]` | `{ id, family, model }` — OpenRouter の識別子。1 ファミリーにつき 1 つの席。 |
| `panelSize` | author-off 方式の審査員（トランスクリプトごと）。デフォルトは **1**。意見の相違を示すために数を増やし、より高いスコアの平均を出すためではない。 |
| `verifiers` | オプションの正規表現リスト（`unparsed`、`refused`、`victory`、`death`。空の場合は推測しない）。席の数：`absorbingMinTurns`（デフォルトは 4）、`noProgressWindow`（デフォルトは 5）、`noOpVerbs`。 |
| `setup[]` | `{ match, answer }`：セットアッププロンプトに対するスクリプト化された回答。 |
| `turns` | 席ごとのプレイ入力数（セットアップの回答と終了入力はカウントしない。デフォルトは 40）。 |
| `persona` | プレイヤーへの説明。 |
| `criteria[]` | `{ id, check }`：ゲーム独自の生存基準。 |
| `screenChars` | 1 ターンあたりに画面に表示される文字数（デフォルトは 6000）。 |
| `playerMemoryTurns` | プレイヤーが確認できる最近のターン数（デフォルトは 8）。 |
| `playerTemperature` | プレイヤーのサンプリング温度（デフォルトは 0.7）。批評家は常に 0。 |
| `runsDir` | 実行結果が書き込まれる場所（デフォルトは `runs`。設定ファイルに基づいて解決される）。 |

設定例：`claude-rpg/dogfood/playtest/claude-rpg.playtest.json`（出荷版の Claude ナレーターは、OpenRouter の Anthropic 互換エンドポイント（`ANTHROPIC_BASE_URL=https://openrouter.ai/api`）を通じて実行される。SDK は `/v1/messages` を追加し、ゲームの `CLAUDE_RPG_MODEL` オーバーライド名が `anthropic/...` 識別子になる）。

### `game.inheritEnv` に関する注意

ゲームプロセスは、小さな許可リストと `game.env` を受け取り、**ただし** `OPENROUTER_API_KEY` は受け取らない。これは常にそうだったわけではない。以前は、このキーがゲームに到達し、画面に表示されるテキストとしてレンダリングされ、そこからプレイヤーのコンテキストと書き込まれたレポートに流れ込んでいた。以前の修正以前の実行結果がある場合は、それらで使用されたキーを公開されたものとして扱う。`inheritEnv: true` は完全な継承を復元する。信頼できるゲームでのみ使用すること。

完全な説明については、[SECURITY.md](SECURITY.md) を参照してください。

## 信頼モデル

**アクセスされるデータ：** プレイテスト JSON、何らかの `game.command` / RPC ブリッジが出力するもの、OpenRouter のチャット完了（プレイヤー + 審査員）、およびランナーが `runsDir`（`transcript.txt`、`critique.json`、`meta.json`、`REPORT.md`、`REPORT.json`）に書き込むファイル。

**アクセスされないデータ：** ランナーはテレメトリを送信せず、分析データを収集しない。ゲームプロセスは、`game.inheritEnv: true` を設定しない限り、`OPENROUTER_API_KEY` を受信しない。外部に書き込まれるものは何もない（`runsDir` 以外）。

**権限：** `game.command` は `child_process.spawn` である。プレイテスト設定は、実行可能ファイルと同等である。シェルスクリプトと同様に確認すること。アウトバウンド HTTPS は、設定された OpenRouter のベース URL のみである。サンドボックスはない。

## テレメトリ

なし。分析データ、クラッシュレポート、または自動通信はない。唯一のネットワーク呼び出しは、モデル用に設定したものである。

## 標準への準拠（ワークフロー標準、スコアは 0〜3）

- **PIN_PER_STEP — 2。** 各席は、使用するモデルの識別子を固定する。プレイヤーと批評家のプロンプトはコード定数であり、設定は再現可能な入力である。OpenRouter はプロバイダーのルーティングを固定しないため、再現はプロンプトが同一になるだけであり、バイトが同一になるわけではない。*修正：各呼び出しで使用されるプロバイダーを `meta.json` に記録する。*
- **ANDON_AUTHORITY — 2。** 処理が停止した場合（`screenTimeoutMs`）、早期に終了した場合、または再試行回数が上限に達した場合、記録された理由とともに終了する。どの席も評価を生成しなかった場合、実行は 4 で終了し、0 ではなくなるため、沈黙した批評の失敗が正常と解釈されることはない。
- **NAMED_COMPENSATORS — スキップ：** ランナーの唯一の成果物は、実行ディレクトリである。それを削除すると、すべてが元に戻る。*ゲーム*の副作用は、ゲーム自体のものであり、ランナーの制御外にある。そのため、プレイテスト設定は、実行可能ファイルと同等として扱われる。
- **DECOMPOSE_BY_SECRETS — 3。** `driver.ts` は観察の境界線、`openrouter.ts` は唯一のネットワーク境界線、`panel.ts` は評価の境界線である。それぞれに独自のテストと、反対側にフェイクがある。
- **UNCERTAINTY_GATED_HUMANS — 3。** レポートは集計するが、決して決定を下すことはなく、自身の不確実性を述べる。意見の相違、範囲の狭さ、サンプルが 1 つしかないことの警告、およびどの批評家も回答しなかった基準は、すべて平滑化されるのではなく、明示される。
- **EXTERNAL_VERIFIER — 3。** 各トランスクリプトは、それを生成しなかったファミリーによって評価される（デフォルトは author-off 方式の 1 つの席。意見の相違を示すために `panelSize` を増やす）。意見の相違は報告される。**このスコアは 3 であったが、コードは 2026-09-14 のスウォームまで逆の動作をしていた。** 批評家は、プレイしたのと同じモデルであった。現在は、この主張が実装と一致しており、`pickJurors` は、常に作成者にフォールバックするのではなく、空の審査員を返す。

## 開発

```bash
npm install
npm run verify      # typecheck (src AND tests) + vitest
npm run coverage    # vitest --coverage
```

182 個のテスト。`tsconfig.test.json` は、ビルド設定にテストファイルが含まれていないために存在し、その結果、どのテストファイルも何らかの形で型チェックされなかった。最初の実行で実際の型エラーが検出された。
