# AIプレイテスト

ターン制ゲームにおける、多様な家族構成を持つAIによるプレイテスト。モデルプレイヤーがゲームをプレイする — ターミナル、疑似ターミナル、またはエンジンへのソケットを通じて — 複数のモデルからなる審査員が各プレイ記録を評価し、レポートは各セッションで実際にプレイされたゲームのどの程度を網羅しているかとともに、その評価結果を集計する。

1人のプレイヤーによる1回のプレイでは、そのプレイヤーが見たことだけがわかる。同じ40ターンを5つの家族がプレイすることで、世界がどのように反応するかを理解できる。

バージョン1.0.0。GitHubで公開。npmにはまだ登録されていない — クローンするか、または関連リポジトリからパスを指定して利用する。

## 誰が評価するのか

まず最初に知っておくべきこと（そして、多くの同様のツールが誤っている点）：**評価者は、自身のプレイを評価しない。** デフォルトでは、各プレイ記録は、別のプレイヤー（`panelSize`、意見の相違を示すためにフラグを立てる — より高いスコアを平均化するためではない）によって評価され、プレイしているプレイヤー自身の評価は、証言として記録される — どこで混乱したか、何を試したか — スコアとしては扱われない。

この区別が重要である。LLMにおける、測定された自己選好の大部分は、ナルシシズムではなく、能力によるものである（37,448組のデータで、能力が一致するコントロールと比較して、約10.4%しか超えない — [Roytburg et al. 2026](https://arxiv.org/html/2601.22548)）。しかし、残りの部分は主観的な領域に集中し、検証可能な領域では消失する — そして、「世界は生き生きとして感じられたか」という問いは、評価基準としては最も主観的である。一方、外部の検証者が評価することで精度が向上するのに対し、自己批判は精度を低下させる：Game-of-24では、自己批判による評価は5%から3%に低下し、適切な検証者による評価では38%に向上する（[Stechly et al. 2024](https://arxiv.org/abs/2402.08115)）。

デフォルトは、**1人の別のプレイヤーによる評価**であり、3人の審査員による評価ではない。[Verga et al. 2024](https://arxiv.org/abs/2404.18796)（PoLL）は、安価な異質な審査員パネルが、7〜8倍低いコストで、人間の合意においてGPT-4を上回ることを示した（κ 0.763 vs 0.627）。これは、1人の大規模な評価者に報酬を支払うことに対する反論であり、3つの家族が3つの独立した評価をもたらすという主張ではない。[Kohli 2026](https://arxiv.org/abs/2605.29800)は、Kishにおいて、7つの家族にわたる9人の評価者を測定し、**n_eff = 2.18**であった。パネル（72.0%）は、最も優れた単一の評価者（71.8%）を上回らなかった。家族間のφは0.389、同じ家族内では0.437であった。`panelSize: 3`では、これは**約1.68の独立した評価**に相当する。Dawid–Skeneはこれを改善しない（Condorcetのギャップの最大11%）。[Kim et al. 2025](https://arxiv.org/abs/2506.07962)は、両方の評価者が間違っている場合、約60%の確率で意見が一致することを発見した。したがって、追加の審査員は、より高いスコアではなく、意見の相違を示すフラグである。**予算は、評価者からプレイ回数に移行する。** `--runs 3`は記述的なものであり、有意性検定ではない。CLIはデフォルトで1回のプレイになるため、テストは1回のみ実行される。n=3では、p<0.05に到達することは不可能（下限`2/2^n` = 0.25）。`docs/research-2.md` §Aおよび`docs/research-3.md`を参照。

これは、評価者が自身の評価から除外されるという事実を覆すものではない。これは、Panickssery / Stechly / Huangに基づいている。

**意見の相違は報告され、平均化されない。** 意見が分かれる場合、通常はゲームが曖昧であるというよりも、評価基準が十分に明確でないことを意味するため、意見の相違は、その回数とともに記録され、各評価者の分散も表示される。

1つの家族のみを評価対象とし、有効な評価者がいない場合、ツールは静かにプレイ記録を著者に返すことはない。評価員は形成されず、レポートには、評価が自己評価であり、それがなぜ信頼性が低いのかが記載される。設定の検証は、1つの家族から2人のプレイヤーを評価対象とすることを拒否する。2つ目の家族が存在することで、別のプレイヤーによる評価が可能になる（[Panickssery et al. 2024](https://arxiv.org/abs/2404.13076)）。

## ドライバー — ゲームがどのように観察されるか

| ドライバー | チャネル | for |
|---|---|---|
| `stdio` | lines | 行指向のテキストゲーム（デフォルト） |
| `pty` | レンダリングされたターミナル**グリッド** | フルスクリーンのTUI（ratatui、ncurses） |
| `rpc` | TCP経由の構造化された状態 | Godot、Unreal、または計測可能なもの |

この順序は、チャネルがどれだけ構造化されているかによって決まり、これは好みの問題ではなく、意図的なものである。アクセシビリティツリーの観察は、[OSWorld](https://arxiv.org/abs/2404.07972)におけるスクリーンショットのみの成功率をほぼ2倍にする（12.24% vs 5.26%）。[BALROG](https://arxiv.org/abs/2411.13543)では、視覚情報を追加することで、いくつかのモデルのパフォーマンスが低下する（GPT-4o 32.34% → 22.56%）。構造化されていないピクセルベースのプレイは、[VideoGameBench](https://arxiv.org/abs/2505.18134)（ゲーム完了率0.48%）でほぼゼロになる。そして、[Voyager](https://arxiv.org/abs/2305.16291)は、依然として最も優れたオープンエンドのゲームエージェントであり、構造化されたAPIを使用し、ピクセルを一度も見たことがない。

したがって、スクリーンショットは、観察におけるオプションの*添付ファイル*であり、唯一のチャネルではない。**ゲームが自身を記述できる場合、そうすべきである** — Godot 4のペーストしてすぐに使用できるautoloadについては、[docs/engine-bridge.md](docs/engine-bridge.md)を参照。`_observation()`と`_apply()`が、記述する必要がある唯一の関数であり、Unrealのルーティングも含まれている。

### なぜ`pty`がテキストゲームでも重要なのか

パイプの下では、Cプログラムのstdoutは完全にバッファリングされるため、「出力がNミリ秒間停止した」というメッセージは、「まだフラッシュされていない」という意味であり、「待機している」という意味ではない可能性がある。PTYは行バッファリングを復元し、準備完了のルールを明確にする。Windowsでは、パイプはConsole APIを通じて描画するゲームからの情報を一切キャプチャしない。

また、リドローがどのように見えるかも修正する。テストTUIで測定した結果、グリッドには**現在の画面の115文字**が表示され、行追加ビューには、プレイヤーが入力した内容が挿入された3つのリドローが積み重ねられ、**416文字**と、*矛盾する3つのHP値*が表示される。モデルは、どれが現在の値であるかを推測する必要がある。

`pty`には、オプションの`node-pty`と`@xterm/headless`が必要である。これらは、WindowsとmacOSにプリビルドされた状態でインストールされる。node-ptyはLinuxでコンパイルされる。これらがなければ、そのドライバーは、インストールコマンドを記述したエラーメッセージを表示して失敗する。それ以外の部分は影響を受けない。

## 各評価者が実際にどれだけプレイを見たか

探索しないモデルプレイヤーは、ほとんど見たことのないゲームについて、自信のあるレポートを作成する。したがって、各プレイには、ターンレコードから計算されたカバレッジブロックが含まれる — 追加の計測やモデル呼び出しは行われない。新規性の曲線と半減期、繰り返し/ループ/自己ループの頻度、アクションのエントロピー、および単純な`thin`/`moderate`/`broad`の読み取りと、その理由が記録される。

これは、失敗が理論的なものではなく、実際に測定されるため、価値があるものです。
タスク指向のLLMエージェントは、**63.4%**の確率で以前のアクションを繰り返し、16.0%のループ率を示します。これは、探索のために*トレーニング*されたエージェントの24.9%/7.7%と比較されます（[Ye et al. 2026](https://arxiv.org/html/2605.16143)）。これを、エージェントの繰り返しが実際にどの範囲に収まるかとして解釈してください。単にエージェントに探索するように促すだけでは、平均パス@1で**+2.57**の改善にしかなりません（[Englander et al. 2026](https://arxiv.org/html/2604.17609)）。アクションのエントロピーが低いことは、効率性よりもむしろ成功率が低いことを示します。したがって、明確な入力が少ない整理されたトランスクリプトは、良い兆候ではなく、警告の兆候です。

## 結果の解釈方法

**ビルドのランキングを重視し、絶対的なスコアを信頼しないでください。** これは、このツールの最も重要な注意点であり、2つの独立した研究から得られます。物語の質を評価するLLMは、システムレベルでτ≈0.70に達しますが、人間の限界である0.73には届きません。一方、物語レベルのτはわずか0.16〜0.25であり、ほとんどBERTScoreを超えていません（[Chhun et al. 2024](https://arxiv.org/abs/2405.13769)）。自動プレイテストも同様の結果を示します。AIのパス率は、95,266人のプレイヤーを対象に、ρ=0.80で人間のパス率と一致します（[Roohi et al. 2021](https://arxiv.org/abs/2107.12061））。ただし、絶対的なエージェントのスキルはまったく転移しません。

したがって、「ビルドBは、*プレイヤーの反応*においてビルドAよりも低いスコアを獲得した」という主張は、このツールで検証できます。「このゲームは生きている：はい」という主張は検証できません。レポートは、この区別を明確に示すように作成されています。

**既知のギャップを明確に記述:** エージェントのプレイテスターによって発見された問題と、人間のプレイテスターによって発見された問題との間の合意を、*体験の質*に関して測定した研究は、私たちが調べた限り存在しません。自動プレイテストは、難易度と能力のみに基づいて検証されます。このツールの中心的な前提、つまりモデルの混乱がプレイヤーの混乱に似ているという考え方は、文献においてどちらの方向にも検証されていません。デッドスポットと混乱を、発見された事実としてではなく、確認すべき手がかりとして扱ってください。

## 仕組み

1. **観察。** ドライバーは、常に`text`、オプションでターミナル`grid`、構造化された`state`、添付ファイル`image`、および現在有効な`actions`を含む、出力`Observation`を生成します。また、それがどのようにプレイヤーのターンであると判断したかを記録します。記録されるのは、ゲームによって送信されるシグナル、ターミナルからの準備完了シグナル、プロンプトパターン、または静止状態の推測です。これにより、知識と推論を区別できます。
2. **スクリプトによる設定。** `setup[].match`の正規表現に一致するプロンプトは、プレイヤーなしで、ターンを消費せずに、設定ファイルから応答されます。これにより、すべてのグループは同じキャラクターから開始します。
3. **プレイヤー**は、前回入力した内容と、それ以降の`playerMemoryTurns`回のやり取りを含む画面を見ます。画面には、`persona`（目標とレジスタ—テスト対象のメカニズムは含まれません）による説明が表示され、プレイヤーは1行で応答します。形式が正しくない応答は、`look`にフォールバックします。
4. **実行。** 観察に`actions`が含まれている場合、クリーンアップされた応答は、`choose`/`key`/`line`にマッピングされます。閉じたセットで一致しなかった場合は、テストフレームワークのイベントとなり、ランナーはゲームターンを消費しません。設定と終了は、`kind:line`のままです。
5. **終了。** `turns`が入力した後、ランナーは`quitInputs`（例：`save`、`quit`）を送信します。これらは*ランナー*の入力であり、ターン数と証拠から除外されますが、生成されたターミナル画面は保持されます。クラッシュまたはセーブの要約は、証拠となります。
6. **審査員**—デフォルトでは、1人の著者席が割り当てられ、温度は0です。審査員は、トランスクリプトを`criteria[]`と比較して評価します。追加の審査員（`panelSize`> 1の場合）がいる場合、意見の相違を指摘します。ただし、より高いスコアに平均化されることはありません。プレイ席自身の評価は、証言として扱われます。
7. **決定的なチェック**は、ターンの記録に対して実行されます。これには、吸収型SCC（Tarjan、トラップとしてラベル付けされることはありません）、無視された入力の帰属、オプションのパーサー/勝利/死亡の正規表現、進行がないウィンドウ、エンティティの出現の指標、および（`state`がオブジェクトの場合）HP/インベントリの不変性などが含まれます。
8. **レポート**は、グループごとの基準、審査員の意見の分割、カバレッジ（サンプリングの指標）、検証ブロック、およびすべてのデッドスポットと混乱をまとめたものを示します。まず審査員の意見が示され、次に著者の証言が示されます。グリフ（`!`、`H(a)`、`repeat`、`loop`）は、ページに凡例として表示されます。

`<runsDir>/<label>/<seat>/`の下のシートごとの成果物：`transcript.txt`、`critique.json`、`meta.json`（ピン`schemaVersion` + `toolVersion`）、`stderr.txt`（ゲームが何かを書き込んだ場合）。`REPORT.md`と`REPORT.json`（`kind: "single-run-report"`）は、ラベルのルートにあります。

## 使用方法

```bash
export OPENROUTER_API_KEY=...
npm run build
node dist/cli.js run path/to/game.playtest.json --label phase9
node dist/cli.js run path/to/game.playtest.json --label smoke --seats mistral --turns 8
node dist/cli.js run path/to/game.playtest.json --label compare --runs 3   # descriptive; cannot reach p<0.05
node dist/cli.js run path/to/game.playtest.json --label rpc --serial       # one game, several seats; needed for RPC until you multiplex
node dist/cli.js report path/to/game.playtest.json --label phase9   # rebuild REPORT.md + REPORT.json from disk
```

`--serial`は、シートを1つずつ実行します。RPCドライバーでは、1つのTCPクライアントを再利用し、シート間で`reset()`を呼び出します。`--serial`がない場合、各RPCシートは独自のプロセスになります。これらが1つのリスニングゲームを共有する場合、競合が発生します。

終了コード：0 OK · 1 使用法 · 2 構成 · 3 プロバイダー（キーが欠落、モデルにエンドポイントがない） · 4 実行エラー（すべてのシートがエラーで終了するか、どのシートも結果を出力しなかった）。エラーは、`error:`と`hint:`を出力します。

## 構成のリファレンス

| key | meaning |
|---|---|
| `name` | playtest name (report title) |
| `driver` | `{"kind":"stdio"}` (default), `{"kind":"pty","cols":100,"rows":30,"readySentinel":"..."}`, or `{"kind":"rpc","port":7777,"host":"127.0.0.1"}` |
| `game.command`, `game.args`, `game.cwd` | ゲームを起動する方法：`cwd`は設定ファイルを参照します。`rpc`の場合、`command`を設定し、`run`はプロセスから`PLAYTEST_BRIDGE_PORT=`を読み取ります（このポートが`driver.port`よりも優先されます）。すでに接続を待機しているゲームに接続するには、`command`を空のままにします。コマンドを持つ2つ以上のシートが必要な場合は、`--serial`を設定します。 |
| `game.env` | ゲーム用の追加環境変数。値が`$NAME`の場合、ランナーの環境変数を読み取ります。 |
| `game.inheritEnv` | ランナーの環境全体をゲームに引き渡します。**デフォルトではオフ**になっています。詳細は下記をご覧ください。 |
| `game.promptPatterns` | 「行を待機中」という意味を持つ正規表現で、末尾を削除した文字列（`stdio`）または表示されているカーソル行（`pty`）に対してテストされます。 |
| `game.promptQuietMs` / `idleQuietMs` / `screenTimeoutMs` | the waiting rule (defaults 800 / 6000 / 180000 ms) |
| `game.quitInputs` | 最後のターン以降に送信された行数（デフォルトは`["quit"]`） |
| `seats[]` | `{ id, family, model }` — OpenRouter個の席；1家族につき1席 |
| `panelSize` | 各記録において、評価者の意見が異なる場合に、その旨を示すために、評価者の数を増やすことができます（デフォルトは1）。ただし、平均点を高くするために評価者の数を増やすことは意図されていません。 |
| `verifiers` | オプションの正規表現リスト（`unparsed`、`refused`、`victory`、`death`。空の場合は推測を行わない）。占有率：`absorbingMinTurns`（デフォルトは4）、`noProgressWindow`（デフォルトは5）、`noOpVerbs`。 |
| `setup[]` | `{ match, answer }` scripted answers for setup prompts |
| `turns` | 1つの座席あたりのプレイ入力回数（設定や終了の操作はカウントしません。デフォルトは40回です）。 |
| `persona` | the player brief |
| `criteria[]` | `{ id, check }`：ゲーム独自の生存基準 |
| `screenChars` | 画面に表示されるキャラクターの数（1ターンあたり、デフォルトは6000） |
| `playerMemoryTurns` | プレイヤーが最近見たターン数（デフォルトは8） |
| `playerTemperature` | プレイヤーのサンプリング温度（デフォルトは0.7）。評価者は常に0。 |
| `runsDir` | 実行結果が書き込まれる場所（デフォルトは`runs`、設定ファイルに基づいて解決される） |

実際に動作する設定例：`claude-rpg/dogfood/playtest/claude-rpg.playtest.json`
出荷されたClaudeのナレーターが、OpenRouterのAnthropic互換バージョンを実行します。
エンドポイント — `ANTHROPIC_BASE_URL=https://openrouter.ai/api`。SDKがこれに追記します。
`/v1/messages` — ゲーム内の`CLAUDE_RPG_MODEL`という名前のオブジェクトを上書きします。
`anthropic/...` スラグ。

### `game.inheritEnv`に関する注記

ゲームプロセスは、小さな許可リストとあなたの`game.env`を受け取り、**ただし**`OPENROUTER_API_KEY`は受け取らない。これは常にそうだったわけではない。以前は、このキーがゲームに到達し、画面に表示されるテキストとしてレンダリングされ、そこからプレイヤーのコンテキストと書き込まれたレポートに流れ込んでいた。もし、その修正前の実行結果がある場合は、それらに使用されたキーを公開されたものとして扱うこと。`inheritEnv: true`は完全な継承を復元する。信頼できるゲームでのみ使用すること。

完全な説明については、[SECURITY.md](SECURITY.md)を参照してください。

## 信頼モデル

**アクセスされるデータ：**プレイテストJSON、何らかの`game.command`/RPCブリッジが出力するもの、OpenRouterのチャットの完了（プレイヤー＋審査員）、およびランナーが`runsDir`に書き込むファイル（`transcript.txt`、`critique.json`、`meta.json`、`REPORT.md`、`REPORT.json`）。

**データは変更されません：** ランナーはテレメトリーデータを送信せず、分析データも収集しません。ゲームプロセスは、`game.inheritEnv: true`を設定しない限り、`OPENROUTER_API_KEY`を受信しません。`runsDir`以外の場所にデータは書き込まれません。

**権限：**`game.command`は`child_process.spawn`である。プレイテスト設定は、実行可能ファイルと同等である。シェルスクリプトと同様に、内容を確認すること。アウトバウンドHTTPSは、設定されたOpenRouterのベースURLのみである。サンドボックスは存在しない。

## テレメトリー

なし。分析データも、クラッシュレポートも、自動送信機能もない。唯一のネットワーク呼び出しは、モデル用に設定したものである。

## 標準への準拠（ワークフロー標準、0〜3で評価）

- **PIN_PER_STEP — 2。** 各座席は、使用するモデルのスラッグを固定する。プレイヤーと審査員のプロンプトは、コード定数である。設定は、再現可能な入力である。OpenRouterは、プロバイダーのルーティングを固定しないため、再現はプロンプトが同一になるだけであり、バイトが同一になるわけではない。*修正：`meta.json`で、各呼び出しで使用されたプロバイダーを記録する。*
- **ANDON_AUTHORITY — 2。** 処理が停止した場合（`screenTimeoutMs`）、早期に終了した場合、または再試行回数が上限に達した場合、記録された理由とともに終了する。いずれかの座席が結果を生成しなかった場合、実行は4で終了し、0で終了することはない。したがって、沈黙した批判的な失敗は、正常に完了したと解釈されることはない。
- **NAMED_COMPENSATORS — スキップ。** ランナーの唯一の成果物は、実行ディレクトリである。それを削除すると、すべて元に戻る。*ゲーム*の副作用は、ゲーム自体のものであり、ランナーの制御外にある。そのため、プレイテスト設定は、実行可能ファイルと同等として扱われる。
- **DECOMPOSE_BY_SECRETS — 3。** `driver.ts`は観測の境界、`openrouter.ts`は唯一のネットワーク境界、`panel.ts`は判断の境界である。それぞれに独自のテストがあり、反対側にフェイクが存在する。
- **UNCERTAINTY_GATED_HUMANS — 3。** レポートは集計するが、決定を下すことはなく、自身の不確実性を述べる。意見が分かれた場合、データが少ない場合、サンプルが1つしかない場合、およびどの審査員も回答しなかった基準がある場合、それらはすべて平滑化されるのではなく、明示的に表示される。
- **EXTERNAL_VERIFIER — 3。** 各トランスクリプトは、それを生成しなかったグループによって評価される（デフォルトでは、1つの著者が異なる座席。`panelSize`を上げて、意見の相違をフラグする）。意見の相違は報告される。**この評価は3点であったが、コードは2026年9月14日のスウォームまで、その逆の動作をしていた。** 批判者は、プレイしたのと同じモデルであった。現在、この主張は実装と一致しており、`pickJurors`は著者にフォールバックするのではなく、空の審査員を返す。

## 開発

```bash
npm install
npm run verify      # typecheck (src AND tests) + vitest
npm run coverage    # vitest --coverage
```

182個のテスト。`tsconfig.test.json`が存在するのは、ビルド設定にテストファイルが含まれていないため、どのテストファイルも何らかのツールによって型チェックされなかったからである。最初の実行で、実際の型エラーを検出した。
